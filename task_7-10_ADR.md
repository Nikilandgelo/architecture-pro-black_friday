### Задание 7. Проектирование схем коллекций для шардирования данных

##### Сводная таблица
|   Коллекция   |  Шард-ключ  | Тип шардирования | Причина                                                                                                                                                                                            |
|:-------------:|:-----------:|:----------------:|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|  **orders**   |  client_id  |   Хэшированное   | Основной паттерн доступа - равенство по client_id (поиск истории заказов клиента). Хэш дает более менее равномерное распределение и targeted-запросы к шардам.                                     |
| **products**  | product_id  |   Хэшированное   | Критичный путь - частые обновления остатков при оформлении заказа. Равномерное распределение важнее, чем targeted-поиск по каталогу (read-путь, может пагинироваться и кэшироваться).              |
|   **carts**   |  owner_key  |   Хэшированное   | Вычисляемое поле на бэкенде (`user_{user_id}` / `guest_{session_id}`), всегда заполнено. Снимает проблему null-значений у гостевых корзин и дает targeted-запросы и для гостя, и для пользователя. |
---

##### Схемы коллекций:
###### orders
```json
{
  "_id": ObjectId("..."),
  "client_id": "user_12345",
  "created_at": ISODate("2026-10-01T10:00:00Z"),
  "items": [
    { "product_id": "sku_001", "price": 1990, "quantity": 1 },
    { "product_id": "sku_045", "price": 450, "quantity": 2 }
  ],
  "status": "processing",
  "total": 2890,
  "geozone": "Moscow"
}
```
**Шард-ключ:** `{ client_id: "hashed" }`

**Обоснование:**
- Основные операции (история заказов пользователя, отображение статуса) всегда фильтруются по конкретному
`client_id` и т.к это равенство, а не диапазон, поэтому хэш подходит лучше range-ключа и дает равномерное
распределение без риска монотонного роста.
- `geozone` рассматривался как альтернативный кандидат с геошардингом, но отклонен, т.к во-первых,
распределение заказов по регионам неравномерно (хотспот на крупных регионах, тот же риск, что и у range-ключа),
во-вторых, пользователь может оформить заказ в одной стране (части страны), а потом переместится и смотреть
историю из другой — зонирование по геозоне сделало бы такие чтения не targeted. Геозона остается обычным полем
документа, не шард-ключом.
- Для запроса конкретного заказа по его собственному `order_id` стоит всегда включать `client_id` в фильтр
(`{ client_id, order_id }`), иначе запрос без шард-ключа уйдет по всем шардам, но т.к. `client_id` у нас
всегда присутствует в рамках взаимодействия с заказами, то это не выглядит большой проблемой.

**Команды:**
```javascript
sh.enableSharding("shop")
sh.shardCollection("shop.orders", { client_id: "hashed" })
```

###### products

```json
{
  "_id": ObjectId("..."),
  "product_id": "sku_001",
  "name": "Смартфон X",
  "category": "Электроника",
  "price": 29990,
  "stock": [
    { "geozone": "Yekaterinburg", "qty": 50 },
    { "geozone": "Kaliningrad", "qty": 30 }
  ],
  "attributes": { "color": "black", "storage": "128GB" }
}
```
**Шард-ключ:** `{ product_id: "hashed" }`

**Обоснование:**
- Два конкурирующих паттерна доступа: 1. Частые обновления остатков по `product_id` - хочет равномерного
распределения и targeted-записи; 2. Поиск по категории с фильтром по цене - хочет группировки по
`{category, price}`. Один ключ не может оптимально обслужить оба паттерна одновременно.
- Приоритет отдан первому паттерну, т.к списание остатков происходит в hot path транзакции оформления заказа,
где латентность и равномерная нагрузка критичны. Поиск же по каталогу - background read-операция, типично
пагинируемая и уже потенциально закэшированная в Redis внутри архитектуры приложения, поэтому ее выполнение
через все шарды кажется приемлемым.
- Для поиска по категории/цене на каждом шарде создается обычный (не shard) составной индекс:
```javascript
db.products.createIndex({ category: 1, price: 1 })
```
- **Опциональное улучшение (CQRS внутри самого MongoDB).**
Если поиск по каталогу во всех шардах все таки станет узким местом при росте нагрузки, можно будет вынести чтение
в отдельную read-модель - например, коллекцию `products_catalog_view`, шардированную по `{ category: 1, price: 1 }`
(диапазонный ключ, оптимальный именно для этого паттерна). Синхронизацию между `products` (write-модель) и
`products_catalog_view` (read-модель) сделать асинхронной через **MongoDB Change Streams**, где фоновый воркер
подписывается на изменения в коллекции `products` и реплицирует нужные поля в read-коллекцию. Это даст небольшую
задержку между остатками и каталогом ценой дополнительной операционной сложности, поэтому данное решение не
входит в базовую реализацию и приведено как дальнейший потенциальный путь масштабирования.

**Остатки по геозонам:** массив `stock[]` требует positional update с arrayFilters для атомарного списания:
```javascript
db.products.updateOne(
  { product_id: "sku_001", "stock.geozone": "Yekaterinburg" },
  { $inc: { "stock.$.qty": -1 } }
)
```

**Команды:**
```javascript
sh.shardCollection("shop.products", { product_id: "hashed" })
```

###### carts

```json
{
  "_id": ObjectId("..."),
  "owner_key": "guest_a1b2c3d4",
  "user_id": null,
  "session_id": "a1b2c3d4",
  "items": [
    { "product_id": "sku_001", "quantity": 1 }
  ],
  "status": "active",
  "created_at": ISODate("2026-10-01T09:00:00Z"),
  "updated_at": ISODate("2026-10-01T09:05:00Z"),
  "expires_at": ISODate("2026-10-02T09:00:00Z")
}
```
**Шард-ключ:** `{ owner_key: "hashed" }`

**Обоснование:**
- Прямое шардирование по `user_id` или `session_id` создало бы хотспот: у всех гостевых корзин значение
`user_id` (у авторизированных значение `session_id`) отсутствует = `null`, и все они оказались бы на одном шарде.
- `owner_key` - вычисляемое на уровне приложения поле (`user_{id}` для авторизованных, `guest_{session_id}`
для гостей), которое всегда заполнено. Это дает равномерное распределение и targeted-запросы для основного
паттерна `{ owner_key, status: "active" }`.
- Слияние гостевой корзины в пользовательскую: `find({ owner_key: "guest_...", status: "active" })` и
`update({ owner_key: "user_...", status: "active" })` - оба запроса targeted (каждый бьет в свой шард по
хэшу своего `owner_key`), фулл скан не требуется ни на одном из шагов. Сама операция слияния остается
кросс-шардовой по природе (две разные корзины на двух, вероятно разных, шардах), выполняется на уровне
приложения в два шага, а не как атомарная multi-document транзакция - это допустимо, так как промежуточное
состояние (гостевая корзина еще не помечена `abandoned`) не нарушает целостность данных.
- TTL-индекс на `expires_at` работает независимо на каждом шарде, дополнительной настройки для шардированной
коллекции не требует:
```javascript
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```

**Команды:**
```javascript
sh.shardCollection("shop.carts", { owner_key: "hashed" })
```


### Задание 8. Выявление и устранение «горячих» шардов
##### Набор метрик, чтобы отслеживать состояние шардов:
- Информация по количеству документов, среднему размеру документа и процент шарда от общего объема коллекции:
```javascript
db.products.getShardDistribution()
```
- Количество чанков на каждом шарде:
```javascript
db.getSiblingDB("config").chunks.aggregate([
  { $match: { ns: "shop.products" } },
  { $group: { _id: "$shard", count: { $sum: 1 } } }
])
```
- Существование `Jumbo` чанков (чанков, которые балансировщик физически не может разбить/перенести):
```javascript
db.getSiblingDB("config").chunks.find({ ns: "shop.products", jumbo: true })
```
- Количество операций `insert/query/update/delete` в секунду по шардам в реальном времени:
```shell
mongostat --host shard1/mongo_shard_1:27018,mongo_shard_1_1:27023,...
```
- Нагрузка ресурсов хоста: CPU, memory, disk IOPS каждой shard-ноды;
- Уровень блокировок и очередей:
```javascript
db.currentOp({ "waitingForLock": true })
db.serverStatus().globalLock
db.serverStatus().wiredTiger.cache
```
- Наличие репликационного лага у реплик:
```javascript
rs.printSecondaryReplicationInfo()
```
##### Механизмы автоматического перераспределения данных и меры устранения дисбаланса:
- `Zone Sharding` - явное разведение "горячих" диапазонов по отдельным шардам, по большему числу нод, чем холодные категории
(`Zone Sharding` работает только если поле, по которому задается диапазон, уже входит в состав текущего шард-ключа коллекции):
```javascript
sh.addShardToZone("shard1", "electronics-zone")
sh.addShardToZone("shard2", "electronics-zone")

sh.updateZoneKeyRange(
  "shop.products",
  { category: "Электроника", product_id: MinKey },
  { category: "Электроника", product_id: MaxKey },
  "electronics-zone"
)
```
- Включение балансировщика шардированных коллекций (в случае если он не активен):
```javascript
sh.getBalancerState()  // текущее состояние балансировщика
sh.setBalancerState(true)  // включение балансировщика

// установка работы балансировщика в определенное время
db.getSiblingDB("config").settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
  { upsert: true }
)

sh.balancerCollectionStatus("shop.products")  // текущий статус миграции конкретной коллекции
```
- Уменьшение размера чанков (`MongoDB 6.0+`, для более старых версий используется глобальная
настройка через `config.settings` с `_id: "chunksize"`):
```javascript
db.adminCommand({
  configureCollectionBalancing: "shop.products",
  chunkSize: 32
})
```
- Составной шард-ключ с категорией как ведущим диапазонным полем и хэшированным
вторым полем для равномерного распределения товаров **внутри** каждой категории
по разным шардам/чанкам за счет хэш-суффикса, устраняя ситуацию, когда вся популярная
категория целиком оседает на одном шарде:
```javascript
sh.shardCollection("shop.products", { category: 1, product_id: "hashed" })
```


### Задание 9. Настройка чтения с реплик и консистентность
|  Коллекция   | Операция чтения                                        | readPreference                                | readConcern                                              | Допустимая задержка репликации  | Обоснование                                                                                                         |
|:------------:|--------------------------------------------------------|-----------------------------------------------|----------------------------------------------------------|:-------------------------------:|---------------------------------------------------------------------------------------------------------------------|
|  **orders**  | История заказов (список и просмотр конкретного заказа) | Secondary                                     | Local                                                    |        Несколько секунд         | Просмотр прошлых заказов, не меняется задним числом, может быть еще потенциально закэширована                       |
|  **orders**  | Статус заказа после его оформления                     | Primary / SecondaryPreferred + Causal Session | Majority (Causal Consistency работает только с majority) |                0                | Чтение после записи, иначе после завершения заказа пользователь может увидеть "заказ не найден"                     |
| **products** | Просмотр карточки товара/каталога товаров              | Secondary                                     | Local                                                    |        Несколько секунд         | Не критичная операция чтения, которая к тому же может быть еще потенциально закэширована                            |
| **products** | Проверка остатка перед покупкой                        | Primary                                       | Majority                                                 |                0                | Риск продажи недоступного товара при чтении неактуальных данных                                                     |
|  **carts**   | Получение текущей активной корзины                     | Primary / SecondaryPreferred + Causal Session | Majority (Causal Consistency работает только с majority) |                0                | Пользователь должен видеть свои правки мгновенно, дабы избежать дубликатов товаров в корзине                        |
|  **carts**   | Слияние корзин при логине                              | Primary                                       | Majority                                                 |                0                | Риск потери товаров гостевой корзины при ее переносе в корзину пользователя, поэтому данные должны быть актуальными |

Поскольку `maxStalenessSeconds` в `readPreference` не позволяет установить значение меньше 90 секунд отставания
реплик для их исключения из операций чтения, контроль за лагом в несколько секунд можно реализовать на уровне
операционного мониторинга, а не клиентской настройки, например, на Prometheus-алерт исходя из показателя
`mongodb_replset_member_replication_lag`. При устойчивом превышении порога задержки репликации нода, например,
может автоматически временно переводиться в `hidden: true, priority: 0` через `rs.reconfig()`, что исключит
ее из read-пула, пока она не догонит кластер, не прерывая при этом саму репликацию.


### Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования
#### 10.1. Критичность данных и применимость Cassandra
##### Критичность по целостности и скорости обработки
| Данные                                              | Критичность к целостности                                                                                    | Критичность к скорости                            |
|-----------------------------------------------------|--------------------------------------------------------------------------------------------------------------|---------------------------------------------------|
| Остатки товаров `(products.stock)`                  | Высокая - overselling напрямую бьет по деньгам и репутации                                                   | Высокая - hot path в пиковую нагрузку             |
| Активные заказы (создание, смена статуса)           | Высокая - нельзя потерять/задвоить заказ                                                                     | Высокая - пиковая нагрузка на создание            |
| Завершенная история заказов (архив)                 | Низкая - read-only, не меняется задним числом                                                                | Низкая - не hot path, фоновое чтение              |
| Каталог товаров (name, category, price, атрибуты)   | Низкая - не денежная операция, несвежесть на пару секунд не критична                                         | Средняя - read-heavy, частично кэшируется Redis   |
| Активные корзины                                    | Высокая - риск дублей товара при неатомарном чтении/записи, риск потери товаров гостевой корзины при слиянии | Высокая - каждое действие пользователя это запись |
| Пользовательские сессии                             | Низкая - эфемерные данные, TTL                                                                               | Высокая - read/write на каждый запрос             |

##### Применимость Cassandra
Критерий смысла применимости - **конкурентная запись многих клиентов в одну и ту же партицию с условием (`IF ...`)**.
Там, где каждый клиент пишет только в свои собственные данные, **Cassandra** подходит даже при требованиях
read-your-own-writes (через `QUORUM`/`QUORUM`, без LWT), однако там, где множество клиентов конкурируют за одну
и ту же запись с условием, **Cassandra** не совсем подходит, т.к единственный механизм атомарного conditional
update - `Lightweight Transactions` (LWT, на основе Paxos), который не рассчитан на высокую частоту конкурентных
апдейтов одной партиции.

| Данные                                    | Применимость Cassandra | Обоснование                                                                                                                                                                                                                                                                                                                                                                                                                    |
|-------------------------------------------|------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Остатки товаров                           | Не подходит            | Нужен `findOneAndUpdate` с условием `qty >= quantity` на одной записи популярного товара - тысячи конкурентных апдейтов в одну партицию. LWT в Cassandra здесь становится узким местом. Остается в MongoDB.                                                                                                                                                                                                                    |
| Активные заказы (создание, статус)        | Не подходит            | Статус заказа меняется последовательно разными сервисами (оплата -> упаковка -> доставка -> возможная отмена), часто с условием ("сменить статус, только если текущий определенный"), что является конкурентным conditional update одной строки, требующий LWT, который дорог под высокой нагрузкой. Остается в MongoDB, где это обычная атомарная `findOneAndUpdate` операция.                                                |
| История завершенных заказов               | Подходит               | Write-once после завершения заказа, дальше только read. Каждый клиент пишет в свою партицию (`client_id`), конкуренции по записи внутри партиции нет.                                                                                                                                                                                                                                                                          |
| Каталог товаров (без остатков)            | Подходит               | Редко обновляется, read-heavy, несвежесть на секунды не критична (та же допустимая задержка, что и в Задании 9 для MongoDB).                                                                                                                                                                                                                                                                                                   |
| Активные корзины                          | Подходит               | Высокая критичность к целостности относится к консистентности **в рамках одной пользовательской сессии** (read-your-own-writes, атомарность слияния), а не к конкурентной записи многих клиентов в одну партицию. Каждый клиент пишет только в свою корзину (`owner_key`), поэтому нужный уровень консистентности достигается обычным `QUORUM`/`QUORUM` на чтение/запись (без LWT), что дешево и не теряет выигрыша в latency. |
| Пользовательские сессии                   | Подходит               | TTL нативно на уровне таблицы, высокая частота записи, низкая критичность к межнодовой консистентности, что является классическим профилем нагрузки для leaderless-БД.                                                                                                                                                                                                                                                         |

**Масштабируемость:** все четыре подходящие сущности выигрывают от consistent hashing Cassandra с vnodes —
добавление ноды перераспределяет только часть token-диапазонов, а не весь датасет целиком, что прямо устраняет
проблему "черной пятницы".

**Геораспределённость:** multi-datacenter репликация через `NetworkTopologyStrategy` нативна для Cassandra и
не требует ручной настройки zone sharding, как в MongoDB, что позволяет обслуживать разные регионы с низкой latency.

#### 10.2. Концептуальная модель
##### order_history
```sql
CREATE TABLE order_history (
    client_id    text,
    order_date   timestamp,
    order_id     uuid,
    items        list<frozen<order_item>>,
    total        decimal,
    status       text,
    geozone      text,
    PRIMARY KEY ((client_id), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC, order_id DESC);
```

**Partition key:** `client_id` — каждый клиент пишет в свою партицию. Распределение по кластеру равномерное,
если `client_id` генерируются без видимой закономерности (а не монотонно возрастающие ID) — хэш-функция партиционера
размазывает разных клиентов по разным нодам независимо друг от друга.

**Clustering key:** `order_date DESC, order_id` - отдает самые свежие заказы первыми без дополнительной сортировки
на чтении, `order_id` - tie-breaker для уникальности строки при совпадающем timestamp.

Партиционирование по `client_id` дает равномерность между *разными* клиентами, но не защищает от перекоса
внутри *одного* клиента, который пишет аномально много заказов за короткое время (бот-спам, скомпрометированный
аккаунт, экстремальный B2B-профиль). Важно отметить, что это не та же проблема, что "черная пятница" из задания, 
т.к. там причина в полном перераспределение данных при добавлении шардов в MongoDB (общий, кластерный
процесс), а не перекос одной партиции. Общая пиковая нагрузка "черной пятницы" (много разных клиентов одновременно
создают заказы) как раз равномерно размазывается по кластеру благодаря consistent hashing — каждый новый клиент
попадает в свою, отдельно хэшируемую партицию, вне зависимости от общего количества запросов в секунду.

**Минимизация решардинга:** consistent hashing с vnodes — при добавлении ноды перераспределяется лишь часть
token-диапазонов, не весь датасет целиком, что напрямую решает проблему, описанную во вводной части задания
(полное перераспределение данных при изменении топологии в MongoDB с range-based sharding).

##### products_catalog
```sql
CREATE TABLE products_catalog (
    category     text,
    price_bucket int,
    product_id   text,
    name         text,
    price        decimal,
    attributes   map<text, text>,
    PRIMARY KEY ((category, price_bucket), product_id)
) WITH CLUSTERING ORDER BY (price_bucket ASC);
```

**Partition key:** `(category, price_bucket)` — composite-ключ, где `price_bucket` - дискретизированный диапазон
цены (`price / 1000`). Это принципиально отличается от прямого использования `category` как единственного
partition key: ценовой диапазон естественным образом разрезает потенциально крупную категорию на множество
меньших партиций, каждая из которых содержит только товары одной категории в одном ценовом сегменте.

**Clustering key:** `product_id` — обеспечивает уникальность строки внутри партиции и позволяет
делать point-lookup конкретного товара, если известны `category` и `price_bucket` (что покрывает основной
сценарий: товар открывается из уже отфильтрованного каталога, где категория и примерная цена уже известны
из контекста навигации).

Почему `(category, price_bucket)`, а не просто `category`. Прямое использование `category`
как единственного partition key воспроизводило бы ровно ту проблему, что описана в Задании 8: если 70% товаров
относятся к одной категории, вся эта партиция физически целиком лежит на одном наборе replica-нод с первого дня.
В отличие от MongoDB, где балансировщик хотя бы потенциально может разнести чанки одной категории по разным шардам,
в Cassandra партиция не делится - это гарантированная hot partition по построению, а не допустимый риск на будущее.
Добавление `price_bucket` в partition key (а не в clustering key) устраняет эту проблему естественным образом,
без искусственного хэш-суффикса: товары одной категории физически распределены по множеству партиций - по одной
на каждый ценовой сегмент. Это дает равномерность, опираясь на уже существующее в данных поле (`price`), а не на
искусственную случайность.

**Минимизация решардинга:** consistent hashing с vnodes - при добавлении ноды в кластер перераспределяется 
лишь часть token-диапазонов, затрагивающих отдельные партиции `(category, price_bucket)`, а не весь датасет целиком.

##### active_carts
```sql
CREATE TABLE active_carts (
    owner_key   text PRIMARY KEY,
    items       list<frozen<cart_item>>,
    status      text,
    created_at  timestamp,
    updated_at  timestamp
) WITH default_time_to_live = 86400;
```

**Partition key:** `owner_key` - та же логика, что и в MongoDB-модели: вычисляемый ключ 
`user_{id}` / `guest_{session_id}`, всегда заполнен, каждый клиент пишет только в свою партицию.

**Clustering key:** отсутствует. В отличие от `order_history` или `products_catalog`, здесь связь
`owner_key -> корзина` строго 1:1 где у каждого клиента в любой момент времени ровно одна активная корзина.
Партиция содержит единственную строку, поэтому упорядочивать внутри нее нечего; `PRIMARY KEY` состоит только
из partition key (`owner_key`), без дополнительных clustering columns.

Горячих партиций нет структурно - одна партиция равна одной корзине одного клиента, равномерность
гарантирована природой ключа.

**TTL на уровне таблицы** воспроизводит поведение TTL-индекса из MongoDB, без необходимости в отдельном фоновом
процессе — Cassandra сама удаляет строку по истечении срока (через tombstone).

##### user_sessions
```sql
CREATE TABLE user_sessions (
    session_id    text PRIMARY KEY,
    user_id       text,
    last_activity timestamp,
    payload       map<text, text>
) WITH default_time_to_live = 1800;
```

**Partition key:** `session_id` — случайный токен сессии, генерируемый при каждом логине независимо от
времени создания или идентичности пользователя. Это основной идентификатор, по которому выполняется самый
частый запрос системы — проверка/обновление сессии на каждом HTTP-запросе. Хэш-функция партиционера
(`Murmur3Partitioner`), примененная к случайному входу, дает равномерно распределенный по token ring'у
выход — соседние по времени создания сессии (например, пиковый трафик логинов утром после открытия магазина)
хэшируются в несвязанные точки кольца и физически расходятся по разным нодам/vnode'ам. Это исключает временной
hot spot, который возник бы при партиционировании по признаку, коррелирующему со временем (например, по timestamp создания).

**Clustering key:** отсутствует. Как и в `active_carts`, связь `session_id -> сессия` строго 1:1 — партиция
содержит ровно одну строку, упорядочивать внутри нее нечего.

**Горячие партиции:** структурно исключены — равномерность гарантирована случайной природой `session_id`, а
не зависит от бизнес-профиля данных (в отличие от `order_history` или `products_catalog`, где перекос мог
возникнуть из-за неравномерного поведения клиентов/категорий).

**Минимизация решардинга:** consistent hashing с vnodes — при добавлении ноды перераспределяется только
часть token-диапазонов. Для `user_sessions` это особенно необременительно за счет короткого TTL —
даже затронутые миграцией партиции естественным образом полностью обновляются/истекают в течение получаса,
минимизируя объем данных, которые вообще могут потребовать переноса в любой момент времени.

#### 10.3. Стратегии обеспечения целостности

| Сущность         | Стратегии                                            | Обоснование                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
|------------------|------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| order_history    | Hinted Handoff + Anti-Entropy Repair (по расписанию) | Данные пишутся раз и читаются нечасто - Read Repair малоэффективен (расхождение не обнаружится, пока запись не прочитана повторно). Ночной Anti-Entropy гарантирует согласованность архива независимо от частоты чтения.                                                                                                                                                                                                                                           |
| products_catalog | Hinted Handoff + Read Repair                         | Read-heavy таблица — Read Repair естественно чинит расхождения на каждом обращении к каталогу, без затрат на полный anti-entropy по всему датасету.                                                                                                                                                                                                                                                                                                                |
| active_carts     | Hinted Handoff + Read Repair                         | Короткоживущие, часто читаемые сразу после записи данные — Read Repair эффективен за счёт частоты обращения к тем же строкам. Anti-Entropy избыточен: к моменту ночного прогона большинство корзин уже истекли по TTL. Важно: read-your-own-writes и атомарность слияния корзин обеспечиваются выбором consistency level (`QUORUM` на запись и чтение) на уровне самого запроса, а не Read Repair — Read Repair лишь ускоряет схождение реплик между собой в фоне. |
| user_sessions    | Hinted Handoff                                       | TTL 30 минут — ни Read Repair, ни Anti-Entropy не успевают принести пользу за такое время жизни данных; цена несогласованности минимальна (максимум — повторный логин).                                                                                                                                                                                                                                                                                            |

**Компромисс latency / согласованность:** Hinted Handoff практически бесплатен по latency (фоновый механизм) и 
применяется повсеместно по умолчанию. Read Repair добавляет небольшую задержку на чтение (сравнение между репликами),
оправданную там, где данные читаются часто и их свежесть важна (каталог, корзины). Anti-Entropy Repair —
самый затратный по ресурсам механизм, поэтому применяется только там, где данные естественным образом читаются редко
(архив заказов) и без него расхождения оставались бы незамеченными годами.
