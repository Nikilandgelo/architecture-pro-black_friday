### Задание 7. Проектирование схем коллекций для шардирования данных

##### Сводная таблица
| Коллекция |  Шард-ключ  | Тип шардирования | Причина |
|:---------:|:-----------:|:---------:|---------|
|  **orders**   |  client_id  |  Хэшированное   | Основной паттерн доступа - равенство по client_id (поиск истории заказов клиента). Хэш дает более менее равномерное распределение и targeted-запросы к шардам. |
| **products**  | product_id  |  Хэшированное   | Критичный путь - частые обновления остатков при оформлении заказа. Равномерное распределение важнее, чем targeted-поиск по каталогу (read-путь, может пагинироваться и кэшироваться). |
|   **carts**   |  owner_key  |  Хэшированное   | Вычисляемое поле на бэкенде (`user_{user_id}` / `guest_{session_id}`), всегда заполнено. Снимает проблему null-значений у гостевых корзин и дает targeted-запросы и для гостя, и для пользователя. |
---

##### Схемы коллекций:
###### orders
```json
{
  "_id": ObjectId("..."),
  "client_id": "user_12345",
  "created_at": ISODate("2026-10-01T10:00:00Z"),
  "items": [
    { "product_id": "sku_001", "price": 1990, "quantity": 1 },
    { "product_id": "sku_045", "price": 450, "quantity": 2 }
  ],
  "status": "processing",
  "total": 2890,
  "geozone": "Moscow"
}
```
**Шард-ключ:** `{ client_id: "hashed" }`

**Обоснование:**
- Основные операции (история заказов пользователя, отображение статуса) всегда фильтруются по конкретному `client_id` и т.к это равенство, а не диапазон, поэтому хэш подходит лучше range-ключа и дает равномерное распределение без риска монотонного роста.
- `geozone` рассматривался как альтернативный кандидат с геошардингом, но отклонен, т.к во-первых, распределение заказов по регионам неравномерно (хотспот на крупных регионах, тот же риск, что и у range-ключа), во-вторых, пользователь может оформить заказ в одной стране (части страны), а потом переместится и смотреть историю из другой — зонирование по геозоне сделало бы такие чтения не targeted. Геозона остается обычным полем документа, не шард-ключом.
- Для запроса конкретного заказа по его собственному `order_id` стоит всегда включать `client_id` в фильтр (`{ client_id, order_id }`), иначе запрос без шард-ключа уйдет по всем шардам, но т.к. `client_id` у нас всегда присутствует в рамках взаимодействия с заказами, то это не выглядит большой проблемой.

**Команды:**
```javascript
sh.enableSharding("shop")
sh.shardCollection("shop.orders", { client_id: "hashed" })
```

###### products

```json
{
  "_id": ObjectId("..."),
  "product_id": "sku_001",
  "name": "Смартфон X",
  "category": "Электроника",
  "price": 29990,
  "stock": [
    { "geozone": "Yekaterinburg", "qty": 50 },
    { "geozone": "Kaliningrad", "qty": 30 }
  ],
  "attributes": { "color": "black", "storage": "128GB" }
}
```
**Шард-ключ:** `{ product_id: "hashed" }`

**Обоснование:**
- Два конкурирующих паттерна доступа: 1. Частые обновления остатков по `product_id` - хочет равномерного распределения и targeted-записи; 2. Поиск по категории с фильтром по цене - хочет группировки по `{category, price}`. Один ключ не может оптимально обслужить оба паттерна одновременно.
- Приоритет отдан первому паттерну, т.к списание остатков происходит в hot path транзакции оформления заказа, где латентность и равномерная нагрузка критичны. Поиск же по каталогу - background read-операция, типично пагинируемая и уже потенциально закэшированная в Redis внутри архитектуры приложения, поэтому ее выполнение через все шарды кажется приемлемым.
- Для поиска по категории/цене на каждом шарде создается обычный (не shard) составной индекс:
```javascript
db.products.createIndex({ category: 1, price: 1 })
```
- **Опциональное улучшение (CQRS внутри самого MongoDB).**
Если поиск по каталогу во всех шардах все таки станет узким местом при росте нагрузки, можно будет вынести чтение в отдельную read-модель - например, коллекцию `products_catalog_view`, шардированную по `{ category: 1, price: 1 }` (диапазонный ключ, оптимальный именно для этого паттерна). Синхронизацию между `products` (write-модель) и `products_catalog_view` (read-модель) сделать асинхронной через **MongoDB Change Streams**, где фоновый воркер подписывается на изменения в коллекции `products` и реплицирует нужные поля в read-коллекцию. Это даст небольшую задержку между остатками и каталогом ценой дополнительной операционной сложности, поэтому данное решение не входит в базовую реализацию и приведено как дальнейший потенциальный путь масштабирования.

**Остатки по геозонам:** массив `stock[]` требует positional update с arrayFilters для атомарного списания:
```javascript
db.products.updateOne(
  { product_id: "sku_001", "stock.geozone": "Yekaterinburg" },
  { $inc: { "stock.$.qty": -1 } }
)
```

**Команды:**
```javascript
sh.shardCollection("shop.products", { product_id: "hashed" })
```

###### carts

```json
{
  "_id": ObjectId("..."),
  "owner_key": "guest_a1b2c3d4",
  "user_id": null,
  "session_id": "a1b2c3d4",
  "items": [
    { "product_id": "sku_001", "quantity": 1 }
  ],
  "status": "active",
  "created_at": ISODate("2026-10-01T09:00:00Z"),
  "updated_at": ISODate("2026-10-01T09:05:00Z"),
  "expires_at": ISODate("2026-10-02T09:00:00Z")
}
```
**Шард-ключ:** `{ owner_key: "hashed" }`

**Обоснование:**
- Прямое шардирование по `user_id` или `session_id` создало бы хотспот: у всех гостевых корзин значение `user_id` (у авторизированных значение `session_id`) отсутствует = `null`, и все они оказались бы на одном шарде.
- `owner_key` - вычисляемое на уровне приложения поле (`user_{id}` для авторизованных, `guest_{session_id}` для гостей), которое всегда заполнено. Это дает равномерное распределение и targeted-запросы для основного паттерна `{ owner_key, status: "active" }`.
- Слияние гостевой корзины в пользовательскую: `find({ owner_key: "guest_...", status: "active" })` и `update({ owner_key: "user_...", status: "active" })` - оба запроса targeted (каждый бьет в свой шард по хэшу своего `owner_key`), фулл скан не требуется ни на одном из шагов. Сама операция слияния остается кросс-шардовой по природе (две разные корзины на двух, вероятно разных, шардах), выполняется на уровне приложения в два шага, а не как атомарная multi-document транзакция - это допустимо, так как промежуточное состояние (гостевая корзина еще не помечена `abandoned`) не нарушает целостность данных.
- TTL-индекс на `expires_at` работает независимо на каждом шарде, дополнительной настройки для шардированной коллекции не требует:
```javascript
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```

**Команды:**
```javascript
sh.shardCollection("shop.carts", { owner_key: "hashed" })
```


### Задание 8. Выявление и устранение «горячих» шардов
##### Набор метрик, чтобы отслеживать состояние шардов:
- Информация по количеству документов, среднему размеру документа и процент шарда от общего объема коллекции:
```javascript
db.products.getShardDistribution()
```
- Количество чанков на каждом шарде:
```javascript
db.getSiblingDB("config").chunks.aggregate([
  { $match: { ns: "shop.products" } },
  { $group: { _id: "$shard", count: { $sum: 1 } } }
])
```
- Существование `Jumbo` чанков (чанков, которые балансировщик физически не может разбить/перенести):
```javascript
db.getSiblingDB("config").chunks.find({ ns: "shop.products", jumbo: true })
```
- Количество операций `insert/query/update/delete` в секунду по шардам в реальном времени:
```shell
mongostat --host shard1/mongo_shard_1:27018,mongo_shard_1_1:27023,...
```
- Нагрузка ресурсов хоста: CPU, memory, disk IOPS каждой shard-ноды;
- Уровень блокировок и очередей:
```javascript
db.currentOp({ "waitingForLock": true })
db.serverStatus().globalLock
db.serverStatus().wiredTiger.cache
```
- Наличие репликационного лага у реплик:
```javascript
rs.printSecondaryReplicationInfo()
```
##### Механизмы автоматического перераспределения данных и меры устранения дисбаланса:
- `Zone Sharding` - явное разведение "горячих" диапазонов по отдельным шардам, по большему числу нод, чем холодные категории
(`Zone Sharding` работает только если поле, по которому задается диапазон, входит в состав текущего шард-ключа коллекции):
```javascript
sh.addShardToZone("shard1", "electronics-zone")
sh.addShardToZone("shard2", "electronics-zone")

sh.updateZoneKeyRange(
  "shop.products",
  { category: "Электроника", product_id: MinKey },
  { category: "Электроника", product_id: MaxKey },
  "electronics-zone"
)
```
- Включение балансировщик шардированных коллекций (в случае если он не активен):
```javascript
sh.getBalancerState()  // текущее состояние балансировщика
sh.setBalancerState(true)  // включение балансировщика

// установка работы балансировщика в определенное время
db.getSiblingDB("config").settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
  { upsert: true }
)

sh.balancerCollectionStatus("shop.products")  // текущий статус миграции конкретной коллекции
```
- Уменьшение размера чанков (`MongoDB 6.0+`, для более старых версий используется глобальная
настройка через `config.settings` с `_id: "chunksize"`):
```javascript
db.adminCommand({
  configureCollectionBalancing: "shop.products",
  chunkSize: 32
})
```
- Составной шард-ключ с категорией как ведущим диапазонным полем и хэшированным
вторым полем для равномерного распределения товаров **внутри** каждой категории
по разным шардам/чанкам за счет хэш-суффикса, устраняя ситуацию, когда вся популярная
категория целиком оседает на одном шарде:
```javascript
sh.shardCollection("shop.products", { category: 1, product_id: "hashed" })
```
